# FinTracker — защита проекта

## 30 секунд

FinTracker — Flutter приложение для учёта личных финансов: счета, доходы, расходы, переводы, бюджеты, цели и долги. Данные сохраняются локально в Hive и синхронизируются с Firestore, чеки — с Firebase Storage. Есть аналитика, экспорт отчётов, карта OpenStreetMap, уведомления, датчик встряхивания и собственный Kotlin канал для диагностики Android. Проект проверяется 77 тестами и GitHub Actions; покрытие — 49,50% при пороге 40%.

## 2 минуты

«Я разработал FinTracker как персональный финансовый менеджер на Flutter. После входа через email или Google пользователь видит общий баланс и счета, добавляет доход, расход или перевод и может прикрепить фотографию чека. Для планирования доступны бюджеты по категориям, накопительные цели и долги с частичными платежами. Аналитика показывает расходы по периодам, а отчёты экспортируются в CSV, Excel и PDF.

Код разделён на представление, доменные сущности и интерфейсы, реализации источников данных и общие настройки. Основное состояние управляется Provider и ChangeNotifier. Для валют я отдельно использовал Riverpod AsyncNotifier: он загружает курсы через Dio, показывает ожидание или ошибку и выполняет конвертацию. Это два самостоятельных подхода без переписывания всей архитектуры.

Hive позволяет работать с уже загруженными данными без сети. SyncController сохраняет изменения локально и отправляет пользовательские коллекции в Firestore при восстановлении связи. Локальный путь чека не используется в облаке: для изображения хранится отдельный путь Firebase Storage. Карта построена на OpenStreetMap и geolocator. Через sensors_plus встряхивание открывает форму операции, а мой Kotlin MethodChannel получает сведения о батарее и Android устройстве.

Я проверил проект unit и widget тестами, анализатором и GitHub Actions. Из 77 тестов все проходят; LCOV — 49,50%. Release APK и AAB собраны с отдельным ключом, подписи проверены. Я отдельно отмечаю ограничения: карта использует OpenStreetMap вместо Google Maps SDK, синхронизация не выполняет слияние конфликтующих полей, а CI не развёртывает приложение автоматически».

## Что показать на демо

1. Вход по email; при возможности — Google Sign-In.
2. Dashboard: баланс, счета, график с подсказкой по дате.
3. Создание дохода/расхода/перевода и изменение баланса.
4. Камера или галерея: приложить и открыть чек.
5. Карта: координаты операции и OpenStreetMap.
6. Аналитика: неделя, месяц, год; коснуться графика.
7. Бюджет, цель и долг с частичным погашением.
8. Курсы валют, конвертация и обработка ошибки сети.
9. Включить Shake to Add и встряхнуть телефон.
10. Диагностика устройства: батарея, модель и Android версия.
11. Открыть [успешный GitHub Actions run](https://github.com/dunanhub/FinTracker/actions/runs/37673945899).
12. Показать `flutter test --coverage` и `dart run tool/check_coverage.dart`.

Заранее подготовить тестовый аккаунт и записи; для камеры, карты, FCM, датчика и Kotlin канала нужен Android телефон или эмулятор с соответствующими возможностями. Уведомления о сроках планируются на Android локально за день до даты, около 09:00.

## Объяснить своими словами

**Архитектура.** Экран вызывает контроллер или Riverpod notifier. Тот работает через интерфейс репозитория, а реализация обращается к Hive, Firebase или REST. Это позволяет менять источник и подставлять fake в тесте.

**Provider и Riverpod.** Provider обслуживает основной работающий функционал; Riverpod полностью управляет валютным экраном. Так выполнено учебное требование продемонстрировать второй подход без переписывания приложения.

**Hive и Firestore.** Hive — быстрая локальная копия для уже вошедшего пользователя. Firestore — облачная копия для другого устройства. Firebase Storage хранит изображения, потому что локальный путь Android не работает на другом телефоне.

**Offline sync.** Локальное изменение записывается в Hive и помечается как ожидающее. Контроллер затем отправляет снимок в Firestore; если сеть недоступна, данные остаются локально. При конфликте одновременных правок нет слияния по полям: ожидающий локальный снимок пытается отправиться первым, иначе применяется облачный снимок.

**Kotlin.** `MainActivity.kt` регистрирует канал `com.example.fin_tracker/native_device`; методы `getBatteryInfo` и `getDeviceInfo` вызывают Android SDK и возвращают данные в Dart.

**Безопасность.** Данные Firestore организованы по UID, правила Storage разрешают пользователю доступ только к своему пути. Ключ подписи, пароли и локальный Firebase JSON игнорируются Git. Развёрнутые Firestore rules нужно подтверждать в Firebase Console: файла правил в репозитории нет.

## Возможные вопросы преподавателя

| Вопрос | Короткий ответ |
|---|---|
| Почему Flutter? | Один код UI для платформ и удобная работа с Material 3 и нативными плагинами. |
| Зачем слои и Repository? | UI не зависит напрямую от Hive или Firebase; контракт можно заменить fake в тесте. |
| Где Dependency Injection? | Репозитории создаются в `main.dart`, передаются контроллерам через конструкторы и Provider. |
| Почему Provider? | Им управляется уже существующая основная часть приложения через ChangeNotifier. |
| Что даёт Riverpod? | Валютный `AsyncNotifier` явно представляет loading, data и error и позволяет переопределить repository provider. |
| Почему используются оба? | Это учебная демонстрация двух полноценных потоков состояния без рискованной миграции всех экранов. |
| Почему Hive? | Локальное хранение и работа с данными после входа без постоянной сети. |
| Зачем Firestore? | Пользовательские данные доступны после входа на другом устройстве. |
| Как решаются конфликты? | Снимками: pending локальный набор отправляется первым, иначе загружается облачный; слияния полей нет. |
| Зачем отдельное Firebase Storage? | Чек — файл; Firestore хранит его облачный путь, а не Android путь к кешу. |
| Что происходит при ошибке Storage? | Операция и локальный чек сохраняются, загрузку файла можно повторить. |
| Есть ли автоматическая отправка push с сервера? | Нет. FCM принимается и сохраняется в истории; напоминания о сроках планируются локально на Android. |
| Почему OpenStreetMap, а не Google Maps? | Картографический сценарий реализован через `flutter_map` и OSM без платёжного Google Maps API; это альтернатива буквальному требованию. |
| Где геолокация? | `geolocator` получает координаты с разрешения пользователя; операция может быть показана на карте. |
| Как работает встряхивание? | `userAccelerometer`: два импульса за 650 мс, порог 12 и пауза 1,8 с. |
| Зачем MethodChannel? | Flutter вызывает собственный Kotlin код для Android BatteryManager и сведений Build. |
| Что означает coverage? | Доля исполненных строк в LCOV от включённых Flutter файлов; это показатель покрытия, а не доказательство отсутствия дефектов. |
| Что проверяет CI? | Форматирование, анализ, тесты, порог 40%, debug APK и Web; автоматической публикации нет. |
| Что показал performance review? | Исправлены повторные вычисления графика, лишняя сортировка для карты и декодирование больших миниатюр; FPS ещё нужно измерить в DevTools. |
| Как защищён release? | Отдельный локальный ключ подписывает APK/AAB; секреты исключены из Git. Подпись проверяется `apksigner`/`jarsigner`. |
| Чем debug отличается от release? | Debug удобен для разработки и не собирает Crashlytics автоматически; release подписан отдельным ключом и включает Crashlytics. |
| Какие ограничения остались? | Нет слияния конфликтов по полям, Web Push и server FCM; Google Maps SDK заменён OpenStreetMap. |
