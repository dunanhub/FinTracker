# Performance review — FinTracker

Проверено 7 октября 2026 года. Это аудит кода и сборок; время кадра, FPS и память на устройстве здесь не измерялись.

## Проверенные участки

- `MainShell`: четыре вкладки сохраняют состояние в `Stack`; переходы используют анимацию прозрачности и масштаба. Подписка на встряхивание отменяется, наблюдатель жизненного цикла удаляется.
- Dashboard и Analytics: обе вкладки наблюдают `FinanceController`; графики строятся из операций при обновлении экрана. Контроллеры анимации и прокрутки освобождаются.
- Transactions: поиск и фильтр создают список подходящих операций, а строки выводятся через `SliverList` с `SliverChildBuilderDelegate`.
- More: список короткий и статический.
- Transaction details и форма создания операции: миниатюры чека; просмотр чека на полном экране.
- Map: маркеры операций и список для привязки места. Список в шторке использует `ListView.separated`; `MapController` освобождается.
- Currency: один `ref.watch(currencyRatesProvider)` получает состояние курсов, `ref.read` вызывает действия. Контроллер ввода освобождается.
- `FinanceController`, `SyncController`, FCM и датчик: места вызова `notifyListeners`, таймер синхронизации и подписки потоков. Синхронизация уже откладывает запись на 1,2 секунды после локального изменения и не запускается из `build`.

## Обнаружено и исправлено

1. Значения графиков расходов вычислялись отдельным проходом по всем операциям для каждого дня или месяца. Теперь `FinanceController` собирает суммы за нужные даты одним проходом и сохраняет прежние даты, подписи и исключение выплат долгов.
2. Экран карты дважды запрашивал `finance.transactions` за одну сборку; getter сортирует копию списка. Теперь экран использует одну копию для маркеров и счётчика.
3. Превью чека декодировало исходное изображение даже для небольшой области. У превью в форме операции и деталях задан `cacheWidth` по ширине экрана и плотности пикселей с пределом 1200 px. Полноэкранный просмотр оставлен с исходным разрешением.

## Оставлено без изменений

- `SliverList` операций уже строит строки по мере прокрутки.
- Малые списки Dashboard и More не требуют ленивой сборки.
- `MainShell` хранит вкладки для сохранения их состояния и анимации. Все четыре экрана остаются в дереве, а `context.watch<FinanceController>()` может обновлять скрытые Dashboard и Analytics. Перед изменением этого механизма нужны замеры в profile mode: скрытие вкладок может затронуть их состояние и переходы.
- На карте маркеры пересоздаются при уведомлении `FinanceController`; их число обычно ограничено операциями с координатами. Если профилирование покажет проблему при большом архиве, стоит вынести производный список маркеров или отслеживать версию геоданных.
- Кеширование всего `AnalyticsSnapshot` не вводилось: оно требует строгой инвалидизации после изменения операций и периода. После одного прохода для сумм графика дополнительный кеш пока не обоснован.
- Firebase/FCM, sensor stream и синхронизация сохраняют существующее управление подписками и таймером.

## Ручная проверка в profile mode

1. Запустить на Android устройстве или эмуляторе: `flutter run --profile`; открыть Flutter DevTools и Performance overlay.
2. Создать или загрузить большой архив операций. Прокрутить Transactions, проверить поиск и переключение фильтров; смотреть время сборки и растрирования кадров.
3. Открыть Analytics, сменить неделю/месяц/год и провести пальцем по графику; проверить кадры при обновлении операций.
4. Открыть Map с множеством операций с координатами, перемещать и масштабировать карту; отдельно учитывать сетевую загрузку плиток OpenStreetMap.
5. Открыть чек в деталях, затем на полный экран. На вкладке Memory сравнить пик выделений памяти и освобождение после закрытия экрана.
6. Быстро переключать вкладки MainShell и переходить в More; проверить пропущенные кадры и сохранение положения прокрутки.
7. В CPU Profiler проверить затраты на построение графиков, фильтрацию операций и карту при сценариях выше.
8. Проверить на узком телефоне и с крупным системным шрифтом; зафиксировать реальные измерения устройства, версии Android и размера архива перед дальнейшей оптимизацией.
